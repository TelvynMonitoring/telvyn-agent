# Paridade de fluxo dos Python checks: Datadog Agent × Telvyn

Estado de pesquisa em 2026-10-01. Escopo: **fluxo de Python checks do Agent 7**, não paridade de todo o produto Datadog, nem reutilização do seu código. Referência de contrato: [AgentCheck base](https://github.com/DataDog/integrations-core/blob/master/datadog_checks_base/datadog_checks/base/checks/base.py), [Python loader Go](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/python/loader.go), [PythonCheck Go](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/python/check.go), [interface Check](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/check/check.go), [rtloader](https://github.com/DataDog/datadog-agent/blob/main/rtloader/README.md), [sender/agregador](https://github.com/DataDog/datadog-agent/blob/main/pkg/aggregator/sender/sender.go) e [scheduler](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/scheduler/scheduler.go). Baseline: `check(instance)` do Agent 7; assinaturas Agent 8 ficam fora deste aceite. A comparação exige paridade de ciclo e semântica, sem copiar código Datadog.

O caminho principal importa o módulo, cria/configura uma instância por configuração, mantém o objeto Python entre execuções, agenda `run()`, emite por chamadas tipadas do SDK ao sender e faz `Commit()` ([loader](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/python/loader.go), [check.go](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/python/check.go), [sender](https://github.com/DataDog/datadog-agent/blob/main/pkg/aggregator/sender/sender.go)). O [rtloader](https://github.com/DataDog/datadog-agent/blob/main/rtloader/README.md) embute CPython via C/C++/cgo; seus pré-requisitos incluem compilador C/C++, pacotes de desenvolvimento Python 3.12 e Go com cgo. O Windows local, `CGO_ENABLED=0` e sem gcc/clang, **não valida** esse runtime; validação exige ambiente Linux preparado. **Também existe** `process_isolation` opcional: `AgentCheck.run()` chama [`run_with_isolation`](https://github.com/DataDog/integrations-core/blob/master/datadog_checks_base/datadog_checks/base/utils/replay/execute.py), cujo filho encaminha chamadas ao agregador/Agent; não é um único JSON final nem sandbox de rede/arquivos. Telvyn hoje usa [factory/processo por execução](../internal/checks/external_python.go), [verificador](../internal/checkpackages/verify.go), [mapper](../internal/checks/external_response.go) e [runner](../integrations/runner.py): **não equivalem** ao caminho principal persistente.

| Área | Contrato observado nas fontes oficiais | Estado Telvyn no stage | Falta / critério de aceite |
|---|---|---|---|
| Runtime/ponte | Caminho principal: CPython embutido, loader persistente, bridge de métodos SDK→sender e `Commit()` ao final; isolamento subprocessual é opção, não substituto do caminho principal ([rtloader](https://github.com/DataDog/datadog-agent/blob/main/rtloader/README.md), [check.go](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/python/check.go)). | `python -I -B runner.py` por execução; um JSON de resposta mapeado em Go. | Implementar equivalência de runtime principal persistente e ponte tipada ao sender/commit; testes golden de sequência SDK→sender, identidade e semântica esperada. Validar build/runtime apenas em Linux com dependências C/cgo; não inferir paridade de subprocesso+JSON. |
| Descoberta/configuração | Loader resolve módulo/classe `AgentCheck`, versão e uma instância por entrada; `Configure` recebe `init_config`, instância, origem/provedor ([loader](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/python/loader.go), [check.go](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/python/check.go)). | `external.python` + `package/version/check`; uma `CheckConfig` com `params` string→string e tags; verificação local. | Preservar `init_config` compartilhado e N instâncias independentes, sem misturar segredos/estado; teste com duas instâncias e intervalos distintos. JSON atual não equivale ao `AgentCheck`. |
| Inicialização/lifecycle | Objeto por instância; `__init__`, inicializações e `check(instance)` recorrente; `Run`, `Stop`, `Cancel`, `Version`, warnings na interface Go ([base](https://github.com/DataDog/integrations-core/blob/master/datadog_checks_base/datadog_checks/base/checks/base.py), [interface](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/check/check.go)). | Processo novo/`collect()` por rodada; scheduler Go agenda; sem objeto Python persistente ou hooks de inicialização/finalização. | Objeto persistente por instância, inicialização uma vez, chamadas repetidas, liberação em unschedule; testes desse ciclo. |
| `gauge` | Última amostra por contexto no intervalo ([submissão Agent](https://docs.datadoghq.com/metrics/custom_metrics/agent_metrics_submission/)). | `gauge` passa pelo mapper para `Metric` protobuf; `PostMetrics` atual codifica Gauge. | Teste golden de duas amostras/contexto e preservação de tempo/tags/host sem converter tipo silenciosamente. `PostRaw`/OTLP existente é possibilidade futura, **não** prova de paridade de tipos, agregação ou tags. |
| `count` | Eventos **do intervalo** são somados; não é valor cumulativo bruto ([submissão Agent](https://docs.datadoghq.com/metrics/custom_metrics/agent_metrics_submission/)). | Mapper ignora `type=count` e marca `partial`; Proxmox rotula `diskread/netin` cumulativos como `count`. | Distinguir contagem por intervalo de contador cumulativo; teste que o primeiro chega como count e o segundo não é somado indevidamente. |
| `rate` / `monotonic_count` | `rate` calcula delta/tempo entre amostras; `monotonic_count` calcula delta de contador crescente e trata queda/reset; `flush_first_value` existe na base ([base](https://github.com/DataDog/integrations-core/blob/master/datadog_checks_base/datadog_checks/base/checks/base.py), [submissão](https://docs.datadoghq.com/metrics/custom_metrics/agent_metrics_submission/)). | Nenhum tipo/estado correspondente no mapper; nova execução Python perde memória local. | Estado por identidade de série entre rodadas, definição de primeira amostra/reset e tipo de ingest compatível; testes em ≥3 rodadas, reset e mudança de tags. Não renomear gauge para rate. |
| `histogram` / `historate` | Métodos tipados distintos da base; amostras repetidas exigem agregação em janela, não gauge singular ([base](https://github.com/DataDog/integrations-core/blob/master/datadog_checks_base/datadog_checks/base/checks/base.py), [sender](https://github.com/DataDog/datadog-agent/blob/main/pkg/aggregator/sender/sender.go)). | Sem emissor/mapper/ingest desses tipos no fluxo externo. | Preservar chamadas SDK e semântica de agregação de cada tipo; testes golden com múltiplas amostras por janela. |
| `distribution` | É sinal distinto de histograma, com amostras brutas agregadas no backend; a [tabela oficial de tipos](https://docs.datadoghq.com/metrics/types/) mostra envio por DogStatsD, **não** um `AgentCheck.distribution()` na base inspecionada. | Nenhum canal no fluxo externo. | Não inventar método padrão `AgentCheck.distribution`; se exigido no Telvyn, especificar canal/tipo separado e teste ponta a ponta, como extensão própria. |
| Service checks / eventos | `service_check` continua compatível, mas com *soft deprecation* para checks novos; `event()` envia objeto ao agregador ([base](https://github.com/DataDog/integrations-core/blob/master/datadog_checks_base/datadog_checks/base/checks/base.py)). | Resposta externa contém métricas/inventário/status, sem encaminhamento de service check ou evento. | Suportar chamadas SDK correspondentes e mapear aos canais reais Telvyn; testes com status/mensagem/tags e evento, sem tratar `status=partial` como evento automaticamente. |
| Logs/cursor | `send_log(data, cursor, stream)` envia log estruturado; `get_log_cursor(stream)` lê cursor persistido por stream; requer recepção de logs configurada ([API oficial](https://datadoghq.dev/integrations-core/base/api/), [guia oficial](https://docs.datadoghq.com/logs/log_collection/agent_checks/)). | Resposta externa não tem canal de log/cursor. | Ponte SDK→log receiver, persistência de cursor por instância/stream e configuração; testes de emissão, retomada após restart e isolamento. Não confundir com stdout/stderr do runner. |
| Helpers HTTP/TLS | `AgentCheck.http` fornece cliente/helper do SDK ([API oficial](https://datadoghq.dev/integrations-core/base/api/)); opções TLS dependem da configuração/helper usado. | Checks locais usam `urllib`/pyVmomi e CA por parâmetro; não implementam API `AgentCheck.http`. | Mapear helpers e comportamento HTTP/TLS **apenas após** verificar assinaturas/opções oficiais específicas; teste de CA/verificação para contrato realmente documentado. Não deduzir equivalência a partir de `urllib`. |
| Metadata | `set_metadata()` mantém cache de metadata do check, enviada periodicamente; há tag/source por check ([base](https://github.com/DataDog/integrations-core/blob/master/datadog_checks_base/datadog_checks/base/checks/base.py), [bridge Go](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/python/datadog_agent.go)). | `inventory`/`coverage` validados mas apenas em `InventorySnapshot()` local; sem contrato de ingest. | Ponte de metadata com destino/identidade/TTL definidos e testes de persistência/atualização e isolamento de tenant. |
| Erros/warnings/diagnósticos | Base sanitiza exceção/traceback; Go coleta erro e warnings por instância; interface expõe diagnósticos ([base](https://github.com/DataDog/integrations-core/blob/master/datadog_checks_base/datadog_checks/base/checks/base.py), [check.go](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/python/check.go)). | Runner usa códigos sanitizados; mapper troca `status=error` por erro genérico; `partial` retorna sucesso ao scheduler; `coverage` só local. | Preservar motivo **sanitizado** e estado parcial observável; teste de dependência ausente, falha parcial e segredo nunca presente em logs/saída. |
| Cancelamento/timeouts | `Cancel` chamado ao desagendar, inclusive concorrente com run; opção de isolamento tem timeout que mata o processo principal, não toda a árvore ([interface](https://github.com/DataDog/datadog-agent/blob/main/pkg/collector/check/check.go), [replay](https://github.com/DataDog/integrations-core/blob/master/datadog_checks_base/datadog_checks/base/utils/replay/execute.py)). | `exec.CommandContext` + timeout do scheduler mata o processo imediato; sem hook Python de cancelamento. | Teste de unschedule durante execução, sem rodada posterior nem vazamento; documentar limite para filhos, sem chamar isolamento de processo de sandbox. |
| Cache | Base tem `read/write_persistent_cache` com namespace da instância, sobrevivendo a restart e invalidando quando configuração muda ([base](https://github.com/DataDog/integrations-core/blob/master/datadog_checks_base/datadog_checks/base/checks/base.py)). | Sem cache persistente do check; processo recriado por rodada. | Implementar cache de instância/configuração; testes de reinício, troca de configuração, separação de instâncias e cursor de logs. |
| Versão/instalação | Integrações Python podem ter versão própria; `integration install/show/remove/freeze` gerencia versão compatível **separada do Agent**, e o guia manda reiniciar o Agent após instalar ([guia oficial](https://docs.datadoghq.com/agent/guide/integration-management/)). | Manifesto local assinado/versionado é verificado; não há instalador, atualização atômica nem rollback automáticos. | Aceite próprio: versão de check consultável, compatibilidade bloqueia pacote inadequado, atualização não troca binário Go. Não atribuir hot reload ou rollback ao Datadog sem fonte. |

Cobertura de Proxmox/vSphere **não mede** paridade do loader/SDK; paridade do loader/SDK **não implica** cobertura de métricas dessas integrações. Os catálogos e configurações oficiais são a lista de comparação futura, não promessa de implementação já concluída.

## Critérios de teste antes de alegar paridade

1. Agent 7 como baseline: runtime principal Python embutido/persistente, loader com `init_config` e duas instâncias, `check(instance)` repetido, cancelamento e `Commit()`; golden tests de chamadas SDK→sender e ordem/identidade. O runner JSON atual não satisfaz este critério.
2. Testes tipados por série/janela para gauge, count, rate, monotonic_count (primeira amostra/reset) e histogram; distribution em canal separado sem inventar método `AgentCheck.distribution()`. Nenhum tipo deve cair silenciosamente em gauge ou ser descartado como sucesso; `PostRaw`/OTLP só conta após teste de semântica e tags.
3. Testes de service check, evento, metadata, `send_log`/cursor, erros/`partial`, cancelamento e cache isolado por instância/configuração; segredos nunca presentes em saída/logs. Verificar helpers HTTP/TLS contra a API oficial antes de declarar equivalência.
4. Teste de pacote: versão e compatibilidade visíveis, assinatura verificada antes da invocação, pacote incompatível recusado; atualização sem recompilar Go. Instalação/offline/rollback permanecem pendências separadas do verificador atual. Testes do runtime principal dependem de ambiente Linux com CPython/C/cgo preparados; não foram executados aqui.
5. Para Proxmox e vSphere, comparar separadamente os nomes, unidades, tipos, tags, recursos, eventos/logs/service checks e opções de coleta com seus catálogos oficiais; fixtures locais não validam cobertura real de hypervisor.

Não há aqui instrução para portar bibliotecas, criar sandbox, regras de segurança novas ou copiar implementação Datadog. Os checks Proxmox/vSphere existentes ainda não demonstram cobertura equivalente; o engine atual ainda não demonstra paridade do fluxo AgentCheck.
